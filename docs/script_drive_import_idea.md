# YAJIRスクリプトドライブとimport機構

## 目的

Pico 2 Wを、USBシリアルからスクリプトを投入するだけでなく、Windowsから見える
USBドライブへスクリプトを置くだけで利用できるYajir実行環境にする。

将来は同じドライブへユーティリティライブラリを配置し、`def_import()`で
スクリプト内ポートを取り込めるようにする。

## 実装済み: YAJIRスクリプトドライブ

Pico 2 Wの通常動作中に、TinyUSBによる次のUSB複合デバイスを提供する。

- CDC: YajirのUSBシリアル入出力
- MSC: Windowsから見える`YAJIR`スクリプトドライブ

BOOTSEL時に見える`RPI-RP2`とは別のドライブである。

### ストレージ構成

- Pico 2 Wの物理フラッシュ: 4 MiB
- ファームウェアのリンカー領域: 先頭3840 KiB
- YAJIRドライブ: 末尾256 KiB
- ファイルシステム: FAT12
- セクターサイズ: 512 bytes
- フラッシュ書き込みキャッシュ: 4 KiB

`PICO_FLASH_SIZE_BYTES`は物理サイズの4 MiBを維持する。リンカー領域だけを
`pico_flash_region.ld`で3840 KiBに制限する。物理サイズ自体を縮めると、SDKの
`flash_range_erase()`と`flash_range_program()`がYAJIR領域を範囲外と判定する。

### 起動動作

1. YAJIRドライブが未初期化ならFAT12で初期化する。
2. TinyUSB CDC+MSC複合デバイスを開始する。
3. ドライブのルートから`AUTORUN.YAJ`を探す。
4. 見つかった場合はロード、コンパイル、実行する。
5. ファイルなし、サイズ超過、読み込み失敗、構文エラーの場合はUSBシリアルの
   スクリプト投入待ちへ戻る。

Yajirがファイルシステムを読むのは起動時だけとする。Windowsでファイルを更新した
後は安全な取り外しを行い、Pico 2 Wを再起動する。

USBシリアルからの`Ctrl+C`によるスクリプト中断と再投入は従来どおり利用できる。

### 現在の制限

- Yajir側が読むファイルは固定名`AUTORUN.YAJ`だけ。
- FAT12のルートディレクトリだけを扱う。
- ロングファイル名には対応しない。
- autorunスクリプトは最大16383 bytes。
- `ls`、`save`、`delete`などのファイル操作CLIは提供しない。
- ファイル管理はWindows側で行う。

## 構想: def_import

`AUTORUN.YAJ`などのトップレベルスクリプトから、YAJIRドライブ上の
ユーティリティファイルを単純挿入する。

```yajir
def_import("UTILPORT.YAJ")

MAIN
    1 -> _GPIO26
    "A" -> _BUZZAR
END
```

`def_import()`はコンパイル時の指示であり、指定された位置へ対象ファイルの内容を
差し込んだ後、完成したソース全体を通常どおりコンパイルする。

### ファイル名

- 懐かしの8.3形式だけを扱う。
- 英字の大文字と小文字は区別しない。
- ルートディレクトリだけを探索する。
- 絶対パス、サブディレクトリ、`.`、`..`は許可しない。
- 例: `UTILPORT.YAJ`、`MOTOR.YAJ`、`MORSE.YAJ`

現在の`utility_ports.yaj`は8.3形式を超えるため、ドライブへ配置する際は
`UTILPORT.YAJ`などの名前を使用する。

### import元の規則

- `def_import()`はトップレベルでのみ使用できる。
- 複数の異なるライブラリを直接importしてよい。
- 同じファイルの重複importはエラーとする。
- import結果は記述位置へ挿入する。
- 展開後の合計サイズをスクリプト容量制限に含める。

### import先の規則

import先は、状態を所有するアプリケーションではなく、スクリプト内ポートを提供する
ユーティリティライブラリとして記述する。

禁止するもの:

- `def_import()`。多段importと循環importを構造的に禁止する。
- `MAIN`
- `INIT`
- `def_alias`
- `GVAR`などのグローバル数値変数
- `SGVAR`などのグローバル文字列変数

許可するもの:

- `def_port()`
- `PORT ... END`
- `ARG`、`SARG`
- ポート内部のローカル変数
- `INVOKER`
- `EXIT`
- 組み込みポートと定数

import先とimport元の連携には`INVOKER`を使用する。ライブラリが呼び出し元の
グローバル状態へ直接依存しないようにし、疎結合を保つ。

ポート名の衝突は通常の重複定義エラーとする。名前空間は導入せず、`_BUZZAR`、
`_MOTOR`、`_GPIO26`のようなライブラリ向け命名規則で整理する。

## 実装案

Pico 2 Wホストのローダーで、`script_load()`を呼ぶ前に次の処理を行う。

1. トップレベルソースから`def_import()`を検出する。
2. ファイル名が8.3形式か検査する。
3. FAT12ルートディレクトリから対象ファイルを読む。
4. import先に禁止構文がないか検査する。
5. `def_import()`の位置へ内容を展開する。
6. 展開後サイズとポート定義数を検査する。
7. 完成したソースを`script_load()`へ渡す。

最初の実装はホスト側プリプロセッサとして成立する可能性が高い。PCホストでも同じ
構文を利用する場合は、ファイル読み込み部分だけをホストコールバックとして分離する。

```c
int host_import_source(const char *name,
                       char *buffer,
                       size_t capacity,
                       size_t *length);
```

将来的には、展開後のコンパイルエラーにimport元ファイル名と元の行番号を表示できる
ソースマップを追加すると、ライブラリ開発時の診断が分かりやすくなる。

## 位置づけ

この機構は汎用ファイルシステムAPIやパッケージマネージャではない。制約された
スクリプト内ポートライブラリを安全かつ手軽に再利用するための、小さなimport機構と
位置づける。
